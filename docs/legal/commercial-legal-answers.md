## CLO-1. CRA и стоимость платного уровня

- **Акты:** CRA (EU) 2024/2847 — ст. 3(13), 3(22), сообр. 15–19, ст. 13 (вкл. 13(8) период поддержки ≥ 5 лет, 13(9) доступность обновлений), 14, 28, 31–33, 64(10), 71, Прил. I–II, VII; https://eur-lex.europa.eu/eli/reg/2024/2847/oj (CELEX 32024R2847). DCD (EU) 2019/770 ст. 7–8; CRD 2011/83/EU ст. 6, 9, 16(m). Дата проверки 2026-11-11 — **UNVERIFIED**.
- **Применимость.** Закрытая лицензия (D-22(3)) исключает FOSS-исключение и режим стюарда. Изготовитель — физлицо в Латвии (D-29). При публично задокументированных планах монетизации распространение, по оценке CLO, **коммерческое с первого публичного релиза** (`latvia-individual-review.md` §3) → ст. 14 действует с 11.09.2026 для продуктов на рынке, основные требования — с 11.12.2027.
- **Что это значит для экономики (FIN-1):** CRA-набор (оценка рисков, техдокументация Прил. VII, SBOM, CVD/SECURITY.md, отчётность ст. 14, бесплатные обновления безопасности на период поддержки, декларация ЕС и CE, хранение 10 лет, модуль A) — **постоянная стоимость продукта**, не зависящая от наличия PREMIUM. Большая часть уже закладывается (CISO, AGENT 09). Платный уровень **добавляет**: (1) DCD/CRD для покупателей-потребителей (соответствие, обновления в «разумно ожидаемый» срок, ответственность ≥ 2 лет, информация до договора, отказ 14 дней); (2) НДС/OSS или MoR; (3) поддержку покупателей и бухучёт; (4) регистрацию деятельности; (5) **не** меняет класс CRA и **не** удлиняет минимальный период поддержки — но обещания в маркетинге (LTS, «пожизненные обновления») становятся договорными.
- **Важное следствие:** вывод PA «ответ CLO-1 может сделать платный уровень нерентабельным» — **неверная постановка**: если CRA-затраты невыносимы, нерентабелен **любой публичный релиз**, а не только PREMIUM. Отказ от платного уровня CRA-стоимость не снимает (кроме слабого аргумента «некоммерческое распространение», которому мешают закрытая лицензия и публичные планы монетизации).
- **Микропредприятие:** самозанятый — «предприятие» по Рекомендации 2003/361/EC → льготы ст. 33 (упрощённая документация), ст. 64(10) (нет штрафа за пропуск 24 ч) — UNVERIFIED.
- **Последствия:** штрафы ст. 64; для физлица — личное имущество; PLD-риск.
- **Рекомендации:** CLO-1.1 считать CRA применимым к FREE с первого публичного релиза; CLO-1.2 период поддержки (B-10) — решение владельца до GATE 13, один для всех уровней; CLO-1.3 обновления безопасности — бесплатно всем (R-03A.5), платный уровень не может их «покупать»; CLO-1.4 SIA до первого публичного релиза — рекомендация (решение владельца). **[ЮРИСТ L-Q3, L-Q15]**

## CLO-2. Модель X-05 «бесплатно лично / платно для коммерческого использования»

- **Акты:** Software Directive 2009/24/EC ст. 4–5 (правообладатель определяет условия использования; минимум прав законного пользователя — ст. 5(1)); UCTD 93/13/EEC ст. 3, Прил. п. 1(j) (одностороннее изменение условий); UCPD 2005/29/EC ст. 6–7, **Прил. I п. 20** (называть продукт «бесплатным», если потребитель должен платить сверх неизбежных затрат); DCD ст. 19 (изменение цифрового контента). https://eur-lex.europa.eu/eli/dir/2009/24/oj , https://eur-lex.europa.eu/eli/dir/2005/29/oj , https://eur-lex.europa.eu/eli/dir/1993/13/oj — **UNVERIFIED**.
- **Анализ:**
  1. **Допустимо**: ограничение сферы использования (личное / коммерческое) — обычное условие проприетарной лицензии (модель PhraseExpress, WinRAR).
  2. **Нельзя ретроактивно**: копии, полученные по EULA, разрешающей любое использование, сохраняют это право; новое ограничение — только для **новых версий** с повторным принятием EULA и без ухудшения уже купленного (UCTD).
  3. **UCPD**: «бесплатно» без чёткой оговорки «только для личного использования» — риск вводящей в заблуждение практики (Прил. I п. 20). Нужна заметная оговорка на сайте и в установщике.
  4. **Определение «коммерческого использования»** (сотрудник на рабочем ПК? фрилансер? студент?) — источник споров. Проверка технически невозможна и **запрещена** (CLAUDE.md п. 1, D-25 — нет телеметрии) → только honor system.
  5. **Совместимость данных:** CC-BY-SA данные (B-1) не могут ограничиваться EULA — оговорка сохраняется.
  6. Для физлица в Латвии — коммерческие лицензии B2B требуют выставления счетов → регистрация деятельности/НДС раньше.
- **Вывод CLO:** законно, но **нерационально** — согласен с рекомендацией PA (не ограничивать FREE; BUSINESS продаёт управление, документы, договор). Если владелец хочет модель — **только**: «организации с > N устройств», с конкретной версии, honor system, ясная формулировка, срок перехода, без технических ограничений.
- **Решение:** владелец (X-05, LEVEL 3). **[ЮРИСТ L-Q6]** — формулировка EULA.

## CLO-3. Офлайн-лицензия (K-37), отказ 14 дней, «истечение не отключает купленное»

- **Акты:** GDPR ст. 4(1), 4(5), 5(1)(c), 13; CRD ст. 6(1), 8(7), 9, 14(4)(b), **16(m)** (ред. Директивы (EU) 2019/2161); DCD ст. 7–8, 16(3)–(4) (контент пользователя при расторжении), 19; CRA Прил. I ч. II п. 8 (бесплатные обновления безопасности). https://eur-lex.europa.eu/eli/dir/2011/83/oj , https://eur-lex.europa.eu/eli/dir/2019/770/oj , https://eur-lex.europa.eu/eli/dir/2019/2161/oj — **UNVERIFIED**.
- **Данные в файле (минимизация):** допустимо — случайный идентификатор лицензии (не производный от e-mail), уровень/набор прав, дата выдачи, необязательная дата окончания **права на функциональные обновления**, для B2B — название организации и число мест (по выбору покупателя), подпись вендора. **Не включать:** e-mail, имя физлица, отпечаток машины, IP, данные платежа. ID связывается с записью покупки у нас/MoR → это **псевдонимизированные ПД** (ст. 4(5)) — раскрыть в политике; файл не передаётся нам (нет онлайн-активации, D-25).
- **Отказ 14 дней:** для цифрового контента без материального носителя право отказа **утрачивается**, если исполнение началось с **предварительного явного согласия** потребителя, **признания** утраты права и (ст. 8(7)) **подтверждения** на долговечном носителе. Без этих трёх элементов — право отказа сохраняется (при нарушении информирования — до 12 мес. продления). При MoR — оформляет MoR; проверить его чекаут. Подписка (непрерывная поставка) — отдельные правила возврата пропорционально.
- **«Истечение не отключает купленное»:** для **разовой** покупки бессрочной лицензии отключение функций после даты — несоответствие (DCD ст. 8) и, вероятно, несправедливое условие; допустима модель «бессрочное право использования + обновления функций N месяцев» при **ясном** раскрытии до покупки. Для **подписки** — прекращение платных функций по окончании допустимо, но: (а) обновления безопасности ядра FREE — продолжаются (CRA); (б) пользовательские макросы/настройки — остаются доступными и экспортируемыми (DCD ст. 16(4)); (в) ничего не удаляется.
- **Рекомендация:** принцип K-37 PA — правильный. CISO-6 — парсер; CLO — тексты преддоговорной информации **[ЮРИСТ L-Q6]**.

## CLO-4. Донат vs покупка (K-22)

- **Акты:** VAT Directive 2006/112/EC ст. 2(1)(c) (облагается поставка услуг **за вознаграждение**), ст. 58; DCD ст. 3(1); CRA сообр. 15 (по памяти — принятие донатов без цели прибыли не делает **FOSS** коммерческим; к закрытому ПО — не помогает). Латвия: Likums «Par iedzīvotāju ienākuma nodokli» (налог на доходы физлиц; режим подарков/дохода от деятельности) — **UNVERIFIED**.
- **Анализ:**
  1. **Чистый донат** (никаких прав, функций, тем, ранних сборок, приоритета) — не продажа: нет DCD/CRD; для НДС — вероятно нет вознаграждения за услугу. Для физлица в Латвии — **доход**, подлежащий налоговому учёту (вероятно, как доход от хоз. деятельности, если связан с продуктом) — **[БУХГАЛТЕР L-Q16]**.
  2. **Донат с бонусами** («Supporter»: темы, ранние сборки, приоритетная поддержка) — **встречное предоставление** → продажа цифрового контента/услуги: DCD, CRD (информация, отказ 14 дней), НДС/OSS, чек. Называть «донатом» — риск UCPD.
  3. **CRA:** продукт закрытый — донаты на статус не влияют (уже коммерческий по CLO-1).
- **Формулировки:** чистый вариант — «Поддержать разработку (добровольно; никаких дополнительных функций или прав не даёт)». Вариант с бонусами — «Supporter Edition — покупка», с полной информацией и через MoR.
- **Платформы:** GitHub Sponsors / Ko-fi / Open Collective — доступность для физлица из Латвии и их налоговые формы (W-8BEN для GitHub/Stripe) — проверить (UNVERIFIED).

## CLO-5. Локальный отчёт администратора (K-43)

- **Акты:** GDPR ст. 4(1), 4(7), 6(1)(f), 13, 24, 25, 35, 88; EDPB/WP29 Opinion 2/2017 on data processing at work (WP249); списки DPIA национальных органов (CNIL — мониторинг активности работников; DVI — список ст. 35(4), UNVERIFIED); Германия — **BetrVG § 87(1) Nr. 6** (совместное решение совета работников по техническим средствам, **пригодным** для контроля поведения/работы — практика BAG толкует широко), § 26 BDSG. https://www.edpb.europa.eu/ , https://www.cnil.fr/ , https://www.gesetze-im-internet.de/betrvg/__87.html — **UNVERIFIED**.
- **Анализ:**
  1. Данные отчёта на устройстве, закреплённом за сотрудником (коды отказов, версия, время), — **ПД сотрудника** (косвенная идентификация через устройство).
  2. Организация, которая включает и собирает отчёт, — **контролёр** (определяет цели и средства). KeySwitch-разработчик **не контролёр и не обработчик**, пока не получает данных (R-01 п.1). Если мы когда-либо будем анализировать такие отчёты в поддержке — станем **обработчиком** (DPA ст. 28).
  3. DPIA — **вероятно**, если отчёт позволяет судить об активности/производительности работника (критерии EDPB: уязвимые субъекты — работники, систематический мониторинг). Германия — совет работников **обязателен** независимо от намерения, т.к. средство «пригодно» для контроля.
- **Требования к дизайну (privacy by design, ст. 25 — для нас как поставщика средств):** выключено по умолчанию; агрегаты на устройство за период, **без меток времени отдельных событий**, без имён приложений/окон, без длины текста, без имени пользователя; локально, экспорт только действием администратора; документация «что собирается» для DPIA заказчика (шаблон), уведомление сотруднику в UI, что отчёт включён.
- **Вывод:** функция допустима при этом дизайне; спрос слабый — согласен с LATER (PA).

## CLO-6. Punto/Caramba в мастере переезда (K-35) и сравнительный маркетинг

- **Акты:** EUTMR (EU) 2017/1001 ст. 9(2), **14(1)(c)** (использование чужого знака для указания назначения товара, если это необходимо и соответствует честной практике), 14(2); Директива (EU) 2015/2436 ст. 14 (аналог для нац. знаков); **Директива 2006/114/EC ст. 4** (условия допустимой сравнительной рекламы); UCPD ст. 6(2)(a). https://eur-lex.europa.eu/eli/reg/2017/1001/oj , https://eur-lex.europa.eu/eli/dir/2006/114/oj — **UNVERIFIED**. Правообладатели и регистрации знаков в ЕС («Punto Switcher» — вероятно Яндекс; «Caramba Switcher») — **не проверены** (TMview/EUIPO недоступны).
- **Мастер переезда (UI):** «Обнаружен запущенный Punto Switcher. Два переключателя раскладки мешают друг другу — выключите один из них» — **ссылочное использование** для описания совместимости → допустимо. Импорт их настроек из файлов пользователя — допустим (интероперабельность), без декомпиляции.
- **Сравнительный маркетинг:** допустим при ст. 4 Директивы 2006/114/EC: сравниваются однородные товары; **объективные, проверяемые** характеристики («работает без сетевых запросов, кроме обновлений» — должно быть верно и подтверждено CISO); не порочить, не паразитировать на репутации, не представлять KeySwitch как «замену/копию». Таблицы «мы vs они» — только факты с датой проверки и источником. Утверждения о чужой приватности/безопасности («Punto шпионит») — **запрет** без доказательств (диффамация, UCPD).
- **Санкционный аспект:** простое упоминание названия продукта российской компании санкций не нарушает (UNVERIFIED — проверить в L-Q8 при любом договорном взаимодействии).

  2. **Бесплатная раздача** утилиты пользователям в РФ/РБ: массовое ПО без контролируемой криптографии, по оценке CLO, **вероятно** не запрещено как таковое, но: автообновления (D-25) — продолжающаяся «поставка»; ст. 5n и перечни ПО расширялись пакетами 2024–2025 — **проверить по актуальному консолидированному тексту**.
  3. **Платные продажи** в РФ/РБ: платёжная цепочка (Visa/MC не работают, ограничения банков) и запреты ст. 5n/12g для юрлиц/госорганов → **не планировать**; MoR обычно сами блокируют RU/BY. Нельзя продавать лицам из санкционных списков (269/2014) — MoR проводит скрининг; при прямых B2B-продажах — **наш** скрининг.
  4. **Платёжные провайдеры (UNVERIFIED — доступность для латвийского физлица проверить у провайдера):** **MoR** — Paddle, FastSpring, Lemon Squeezy (Stripe), Stripe Managed Payments; **процессоры** (мы — продавец, сами НДС/OSS) — Stripe (Латвия поддерживается — UNVERIFIED), PayPal, Paysera (LT). Рекомендация: B2C — **MoR** (снимает НДС-OSS, чек-аут CRD, санкционный скрининг); B2B — прямой счёт/договор после регистрации деятельности (обратное начисление НДС внутри ЕС).
  5. **Региональные цены:** внутри ЕС для ПО — вероятно допустимы благодаря исключению ст. 4(1)(b) Geo-blocking Reg. (UNVERIFIED); запрет дискриминации по способу оплаты (ст. 5) действует; потребителям — цена **с НДС**. Вне ЕС — свободно, с учётом санкций.
- **Рекомендации:** CLO-7.1 до любой продажи и до договора с платёжным провайдером — **[ЮРИСТ L-Q8]** (с учётом латвийского гражданства/резидентства владельца); CLO-7.2 в EULA/ToS — санкционная оговорка; CLO-7.3 решение владельца: рынки платных продаж (рекомендация CLO — ЕС/ЕЭЗ + страны без санкций; RU/BY — только бесплатно и только после L-Q8).

## CLO-8. SignPath Foundation и программы «для OSS» (K-25)

- **Источники:** https://signpath.org/ (условия SignPath Foundation), Certum Open Source Code Signing — **недоступны / не прочитаны (UNVERIFIED)**; по памяти CLO: SignPath Foundation бесплатно подписывает **только OSS-проекты под OSI-одобренной лицензией** без проприетарных компонентов, с прозрачной сборкой из публичного репозитория; Certum Open Source — сертификат для разработчиков **открытого** ПО.
- **Вывод:** закрытая лицензия (D-22(3)) → **неприменимо** (подача заявки с закрытой лицензией была бы недобросовестной). Публичность репозитория (D-09) не делает код открытым.
- **Альтернативы для физлица в Латвии (`latvia-individual-review.md` §5):** IV/OV-сертификат коммерческого CA с облачной подписью или токеном (имя владельца видно в UAC); **Azure Artifact Signing** — физлицам только США/Канада, организациям ЕС — да (после SIA; UNVERIFIED-secondary). K-25 (проверяемая сборка, provenance) — **не зависит** от SignPath: GitHub artifact attestations/SLSA provenance + хэши — допустимы для закрытого ПО (условия GitHub — UNVERIFIED).
- **Решение:** L3-U4 — CISO + владелец (бюджет D-22(6)).
