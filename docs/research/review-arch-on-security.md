### 1.4 Буфер обмена и порядок методов записи

1. **SendInput как основной путь (SR-10) — ПРИНЯТЬ С ИЗМЕНЕНИЕМ.** Принимаю: для неизвестных приложений вставка через буфер запрещена; W3 предпочтительнее W2. Изменения:
   - **W1 (`EM_REPLACESEL(TRUE)`) остаётся первым.** Буфер он не трогает, операция атомарна, отмена документирована [DOC]. По всем угрозам ST-01…ST-07 он не хуже SendInput, а по ST-07 (фокус уходит посреди ввода) — строго лучше. Аудит W1 не оспаривает.
   - **Порог W3 не 5 000 символов, а параметр профиля:** по умолчанию 200, максимум 5 000, значение для профиля поднимается по замерам S-2. Причины: (а) длинный ввод увеличивает окно ST-07, а сам аудит в AF-04 называет массовый ввод «клавиатурным флудом»; (б) в Chromium/Word откат идёт по символам или словам — нарушение D-12; (в) 5 000 символов = 10 000 событий, при обработке ~1 мс/символ [UNVERIFIED] это ≥ 5 с — дольше дедлайна операции 1,5 с (AV2 §4.2). Итог: W1 → W3 (≤ порога профиля, без `\r\n\t`) → W2 (только приложения с подтверждённым профилем) → отказ. В [FR]:390 у неизвестного профиля стоит `allows_paste = true` — меняю на `false`.
2. **Белый список форматов (SR-13) — ПРИНЯТЬ**, лимит 16 МБ вместо моих 32. Следствие: после копирования из Office (OLE-форматы `Embed Source`, `Object Descriptor`) путь W2 будет запрещён. Это приемлемо при W3 на первом месте. **ОСПОРИТЬ формулировку** «отложенная отрисовка → не трогать». Узнать, что чужой формат отложен, можно только вызвав `GetClipboardData`, который сам запускает отрисовку; отдельного API для проверки нет [DOC: Clipboard Operations; UNVERIFIED дословно]. Исполнимая замена: перед snapshot проверить `IsHungAppWindow(GetClipboardOwner())`; читать только форматы из белого списка; дедлайн 500 мс. Остаточный риск: если владелец завис в `WM_RENDERFORMAT`, наш поток, открывший буфер, тоже повисает, и буфер обмена остаётся занятым для всей системы. `CloseClipboard` из другого потока не поможет. Поток помечается «отравленным», операция завершается отказом. S-2 обязан измерить этот сценарий.
3. **Метки (SR-14) — ПРИНЯТЬ**, исправляю [FR] §5.9: метки исходных данных сохраняются в snapshot и восстанавливаются один к одному. Своё правило «добавлять запрет истории при restore» оставляю как дополнительное: оно только строже. Запрет W2 в `SM_REMOTESESSION` — принять (консервативно, на удобство почти не влияет).
4. **Seq под `OpenClipboard` — ПРИНЯТЬ.** Ожидаемый номер — значение после нашего `SetClipboardData`; отрисовка по delayed rendering номер не меняет [DOC]. Порядок: `OpenClipboard` → сравнить seq → `EmptyClipboard`/`SetClipboardData` → `CloseClipboard`.
5. **Сигнал завершения — ПРИНЯТЬ, свою позицию меняю.** В [FR] §5.10 (шаг 5) и в состоянии `PasteNotConsumed (буфер восстановлен)` (AV2:360) — ошибка. Если `WM_RENDERFORMAT` нет, приложение ещё может прочитать буфер позже, и после «слепого» восстановления в поле попадёт прежнее содержимое (ST-01). Новая логика:
   - restore только после `WM_RENDERFORMAT`, пришедшего **после** нашего Ctrl+V, **и** пост-проверки `Tri::Yes`;
   - если пост-проверка дала `Unknown`, restore делается только по профилю, где сигнал подтверждён в S-2;
   - если сигнала нет: подставить реальные данные вместо отложенных (поздняя вставка даст ожидаемый текст), не восстанавливать и уведомить пользователя.

   Цена — потеря прежнего содержимого буфера. Это решение владельца (§3, п. 1).

### 1.5 Stdlib CPython: память или read-only preopen

- **Почему read-only preopen оказался слабее, чем я оценивал.** Он опирается на проверку `DirPerms/FilePerms` в `wasmtime-wasi`, а аудит приводит её обходы в 2026 (RUSTSEC-2026-0149/-0188/-0352; ссылки сам не перепроверял). Защиту в глубину даёт ACL ОС: SID контейнера получает только чтение. Но тогда (а) установщик должен выставлять ACE (лишний привилегированный шаг), (б) хэш каталога пришлось бы проверять на каждом старте, (в) в процесс песочницы попадает вся ФС-подсистема `wasmtime-wasi`.
- **Целевой вариант (A):** stdlib — `python314.zip` через `include_bytes!`. Хост реализует read-only подмножество preview1 поверх неизменяемого дерева в памяти: `path_open` только `O_RDONLY`, `fd_read`, `fd_seek`, `fd_readdir`, `fd_filestat_get`, `path_filestat_get`, `fd_prestat_*`, `fd_close`. Все изменяющие вызовы возвращают `ENOTCAPABLE`/`EROFS`. Получается ~1–2 тыс. строк безопасного Rust без `unsafe`, плюс fuzz-цели (ST-24). Если писать **весь** нужный набор preview1 самим (clock, random, args/env пустые, `fd_write` в буфер ≤ 64 КиБ, `poll_oneoff` с бюджетом, `proc_exit`), из графа уходит `wasmtime-wasi`: меньше зависимостей, импорты закрыты по построению (SR-43), AF-03 решён. Альтернатива — переопределить только ФС-импорты поверх `wasmtime-wasi` через shadowing в `Linker`. Её не рекомендую: таблица дескрипторов делится с `wasmtime-wasi`, абстракция протекает.
- **Ускорение (A+):** снимок предынициализации через `wasmtime-wizer` / `wasmtime wizer`. Wizer влит в репозиторий Wasmtime, crate `wasmtime-wizer` публикуется [WEB: README bytecodealliance/wizer; docs.rs wasmtime-wizer 45.0.1]. Это инструмент только для сборки в CI, в runtime его нет. Снимок с уже импортированной урезанной stdlib сокращает холодный старт и делает реальным Pulley (§1.6). Риск: в снимок попадают seed хэшей и состояние PRNG — их нужно пересевать при старте. Стоимость и совместимость с CPython 3.14 — [UNVERIFIED], проверяется в S-3.
- **Запасной вариант (B)**, только если (A) не уложится в S-3: preopen каталога, в котором лежит **один** файл `python314.zip`; права `FilePerms::READ`, ACL контейнера — только чтение; SHA-256 файла проверяет хост до запуска. Требует повторного одобрения Security.
- QuickJS stdlib с ФС не нужна; для JS — ноль preopen и без ФС-импортов.

### 1.6 JIT и ACG / win32k lockdown

- ACG (`ProhibitDynamicCode`) запрещает делать память исполняемой. Он несовместим не только с JIT Cranelift/Winch, но и с загрузкой предкомпилированного `.cwasm`: `Module::deserialize` тоже отображает код как RX во время выполнения [WR, UNVERIFIED на Windows]. С ACG совместим только Pulley (интерпретатор).
- Производительность: Pulley — это интерпретация интерпретатора (CPython/QuickJS внутри Pulley). Ожидаю замедление в разы и больше [UNVERIFIED]. Без снимка Wizer старт CPython, скорее всего, не уложится в бюджет 2 с.
- Важная оговорка: Cranelift — Tier 1, Pulley — Tier 2 [DOC: stability-tiers]. «ACG + Pulley» меняет уровень зрелости и покрытия фаззингом исполнителя на ещё один барьер в ОС. Какой вариант безопаснее, не очевидно. Покрывает ли security-политика Wasmtime Tier 2 так же, как Tier 1, я не проверял (S-3, чтение `docs/security.md`).
- Позиция: модель безопасности **не должна зависеть от ACG** (LPAC + Job + win32k lockdown достаточны как второй слой). ACG — дополнительное усиление. Win32k lockdown обязателен: Wasmtime на Windows использует `VirtualAlloc` и vectored exception handlers (kernel32), GUI не нужен. Условие — статический CRT и отсутствие `user32` в импортах `ks-sandbox.exe`; проверка в CI через `dumpbin /imports`.

### 1.7 WER и panic handler

- **ПРИНЯТЬ С ИЗМЕНЕНИЕМ.**
  - `WerAddExcludedApplication` пишет в HKCU и не может выполняться из AppContainer. Его вызывает основной процесс (или установщик) для **обоих** exe; деинсталлятор запись удаляет.
  - Флаг называется `WER_FAULT_REPORTING_FLAG_NOHEAP` (в SR-84 имя неточное). `WerSetFlags` вызывается в каждом процессе.
  - При `panic = "abort"` std на Windows завершает процесс через `__fastfail`: обработчики исключений при этом не вызываются, процесс уходит сразу в WER [WR, UNVERIFIED]. Поэтому исключение из WER — единственная мера на этом пути, и crash-тест обязан проверить именно его, а также трап Wasmtime и `DIE_ON_UNHANDLED_EXCEPTION` в песочнице.
- Panic hook — только `file:line`. Ставится в каждом бинаре (`keyswitch`, `ks-sandbox`), в библиотеках не ставится. Корпоративные `LocalDumps` (HKLM) сильнее наших мер — честно описать в README.

## 4. Влияние на спайки

**S-2 (Windows integration probe), дополнительно к [FR] §8:**
1. Тестовое окно читает буфер с задержкой 0/50/500/2000 мс: прежнее содержимое **ни разу** не оказалось в поле. Сигнал `WM_RENDERFORMAT` приходит после Ctrl+V в Edge/WebView2/Electron/WPF/Qt/Win32; отдельно — от процесса-монитора буфера.
2. Snapshot по белому списку; фикстура «буфер с метками» — метки после restore на месте; гонка seq (второй процесс меняет буфер между проверкой и restore) — restore не выполнен.
3. Зависший владелец буфера с delayed rendering: время блокировки, судьба «отравленного» потока, занят ли буфер для других процессов.
4. W3: пропускная способность (символов/с) и гранулярность Undo на фикстурах при 200/1000/5000 символов — данные для порога профиля; второй процесс забирает foreground через N мс — в чужое окно ушло ≤ 1 пакета; VK_RETURN/0x0D = 0 при тексте с `\n`.
5. Окно выбора с `WS_EX_NOACTIVATE` + временные хоткеи: фокус поля не меняется; хоткеи сняты после таймаута и после аварийного выхода из операции.
6. Распознавание паролей: `type=password`, CSS-маска, `autocomplete=one-time-code` — `GetText` вызван 0 раз.
7. Различимость `<input>` и `contenteditable role=textbox` через UIA (§3, п. 6).
8. Отказ при собственном повышенном токене; валидатор хоткеев с `VkKeyScanEx` (немецкая раскладка, AltGr).
9. Crash-тест (фича `test-hooks`) для `keyswitch.exe`: `panic=abort`/`__fastfail` → нет дампа в `CrashDumps`/`ReportArchive`.

**S-3 (sandbox), дополнительно к AV2 §9.1:**
1. CPython 3.14 WASI стартует с stdlib из памяти (вариант A): host-preopen нет; импорты модуля ⊆ утверждённого списка; запись/переименование/симлинк в `/Lib` → ошибка, хэш zip не изменился. Стоимость реализации (строки, fuzz) и, отдельно, вариант A+ (Wizer): время старта, пересев PRNG/хэшей.
2. Матрица «Cranelift / Pulley × AppContainer / LPAC × win32k lockdown / ACG»: стартует ли процесс, время холодного/тёплого старта и выполнения типовых JS/Python макросов, RAM. Применим ли `.cwasm` при ACG.
3. Импорты `ks-sandbox.exe` без `user32`/`gdi32`; статический CRT; ACL каталога для SID LPAC.
4. Самопроверка (SR-56) и набор H-01…H-40 на `windows-latest`; `QueryInformationJobObject` подтверждает все UI-ограничения и лимиты.
5. Дедлайн: `poll_oneoff`/sleep-цикл, бесконечный цикл, рекурсия → завершение ≤ 2,5 с, процесса после дедлайна нет (`TerminateJobObject`).
6. Протокол: proptest/fuzz приёмника (10⁶ сообщений), кадр > 64 КиБ, ответ после дедлайна, повтор `request_id`.
7. Трап Wasmtime / паника / `__fastfail` в песочнице → нет дампа; panic hook без payload.
8. Сборка `python.wasm`/`qjs` в CI из закреплённых SHA и WASI SDK по хэшу; встроенный хэш совпадает с пересобранным; изменённый байт → отказ загрузки.
9. Прочитать `docs/security.md` Wasmtime: покрывает ли политика Tier 2 (Pulley) — вход для решения §3, п. 4.
