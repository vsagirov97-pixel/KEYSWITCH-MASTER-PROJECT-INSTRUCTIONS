## 3. Процедура security-ревью PR

### 3.1 Классификация PR (определяет автор, подтверждает AGENT 07)
| Класс | Что входит | Кто ревьюит | Блокирующая подпись |
|---|---|---|---|
| **S0** | Только документация вне `docs/SECURITY_REVIEW.md`/`docs/security/`, стили, тексты UI без логики | не требуется (общее ревью) | — |
| **S1** | `crates/ks-core` (без новых зависимостей), фронтенд без IPC и без изменения конфигурации, тесты | AGENT 07 — чек-лист базовых контролей (`SECURITY_REVIEW.md` §6) | AGENT 07 |
| **S2** | `ks-platform-win`, `ks-engine` (политики), буфер/фокус/запись, `ks-sandbox*`, `ks-storage`, журналирование, любые IPC-команды; `tauri.conf.json`, `capabilities/`, CSP; `Cargo.toml`/`Cargo.lock`, `package*.json`, `deny.toml`; `.github/workflows/`, установщик, манифест | AGENT 07 — полный `/security-gate` + профильный специалист (S-A для песочницы, S-B для Windows, S-D для Tauri/UI, S-E для поставок/CI) | **CISO** |
| **S3** | Закрытие gate/спайка, принятие остаточного риска, исключение по Q-3, изменение решений D-xx с влиянием на безопасность, релиз | CISO лично (+ отчёты 07 и специалистов) | **CISO**; Critical/High остаток — **владелец** |
Пути S2 предлагается закрепить в `.github/CODEOWNERS` (файл — зона AGENT 09/PD; CISO не редактирует).

### 3.2 Критерии блокировки (любой — BLOCK)
1. Новая находка Critical или High, или PR ухудшает открытый Critical/High.
2. Нарушен любой пункт базовых контролей (`SECURITY_REVIEW.md` §6).
3. Нет доказательств проверки (лог CI/команда) для заявленного результата; «не проверено» выдано за «проверено».
4. CI красный или `scripts/check.sh` не приложен.
5. PR затрагивает файлы другого активного потока или смешивает несвязанные изменения.
6. Для S2/S3: нет записи в реестре (новый риск без ID) или не обновлён статус затронутых SEC-xx.
Medium-находка не блокирует, если заведена в реестр с владельцем и сроком и CISO её принял/запланировал; Low/Informational — фиксируются в отчёте ревью.

### 3.3 Сроки (SLA, от запроса ревью)
| Класс | Первый ответ | Вердикт |
|---|---|---|
| S1 | в том же рабочем цикле Orchestrator | ≤ 1 рабочий день |
| S2 | ≤ 1 рабочий день | ≤ 2 рабочих дня (≤ 1 при повторном ревью исправлений) |
| S3 (gate) | ≤ 1 рабочий день | ≤ 3 рабочих дня |
| Security-патч по Q-3 | ≤ 4 ч | ≤ 24 ч |
Просрочка SLA не означает одобрения: PR остаётся в статусе Security Review, PD эскалирует CISO.

### 3.4 Формат результата ревью
Вердикт **PASS / PASS WITH CONDITIONS / BLOCK**; находки с ID (новые — `SEC-xx` в реестре), уровнем, файл:строка, рекомендацией и методом проверки; раздел «проверено (как, где) / не проверено (почему)». Отчёт — комментарий в PR и, для S3, файл `docs/security/review-<тема>-<дата>.md`.

### 3.5 Повторные проверки по расписанию
- Еженедельно (после ввода `schedule` в CI, SEC-37): `cargo deny`, `npm audit` — новые advisory → реестр за ≤ 1 рабочий день, SLA §4.2 `SECURITY_REVIEW.md`.
- На каждом gate — пересмотр всех Accepted рисков (SEC-12-R, SEC-24-R) и статусов.
