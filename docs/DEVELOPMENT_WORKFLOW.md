# DEVELOPMENT_WORKFLOW — правила выполнения, передачи и проверки задач

Действует с 2026-11-10 (директивы V3 → V7). Обязателен для всех агентов.

## 1. Жизненный цикл задачи
`Backlog → Ready → In Progress → Review → Security Review → Legal Review → QA → Done`; из любого статуса — `Blocked` (с причиной).
- **Ready:** у задачи есть ID, исполнитель, руководитель, проверяющий, зависимости закрыты, критерии приёмки записаны.
- **Review:** руководитель команды (или назначенный Senior) проверяет результат по критериям.
- **Security Review:** обязателен, если задача затрагивает: Win32/UIA, буфер, хоткеи, ввод, пользовательский текст, Tauri capabilities/CSP, песочницу, зависимости, хранение, логи/дампы, обновления, установщик, CI. Проводит CISO или назначенный им специалист.
- **Legal Review:** обязателен для новых зависимостей и данных, текстов соглашений и политики, обработки данных, телеметрии/сети, распространения, монетизации, названия/брендинга, шрифтов/иконок. Проводит CLO.
- **QA:** QA Engineer фактически запускает тесты/сценарии и прикладывает вывод.
- **Done:** только после подтверждённых проверок; сообщение исполнителя «готово» не является основанием.
- Дефект на любой проверке → задача возвращается исполнителю с записью дефекта (ID, шаги, ожидаемое/фактическое, приоритет), затем повторная проверка. Известные критические дефекты не накапливаются.

## 2. Поля задачи (`docs/BACKLOG.md`)
ID · название · описание · приоритет (P0 блокирует gate / P1 нужно в MVP / P2 желательно) · исполнитель · руководитель · проверяющий · зависимости · критерии приёмки · порядок · статус · ссылка на результат · QA · Security · Legal.

## 3. Git и PR
- Один поток = одна ветка (`spike/*`, `feat/*`, `fix/*`, `chore/*`, `docs/*`) = один PR. Параллельные потоки не правят одни и те же файлы.
- В описании PR: связь с задачей, что проверено (как/где) и что не проверено, вывод `scripts/check.sh`, ссылки на CI.
- Слияние в `main` — только владелец (или с его явного согласия) после зелёного CI и требуемых ревью. Force-push в `main` запрещён.
- Новая зависимость: обоснование (назначение, лицензия, риск), точная версия не моложе 2 недель; исключение — security-патчи по процедуре CISO; `cargo deny` и `npm audit` зелёные; Legal Review.

## 4. Проверки и доказательства
- Хост облачной сессии — Linux: Windows-поведение проверяется только Windows CI или ручной приёмкой владельца. Каждый отчёт разделяет (V4): автоматически проверено (Linux / Windows CI, ссылка на job) / проверено вручную / не проверено / не поддерживается.
- Результаты тестов не выдумываются. «Код написан» ≠ «задача выполнена» ≠ «gate закрыт».

## 5. Обязательные участники по моментам
| Момент | Участники |
|--------|-----------|
| Новая функция | AGENT 10 (аналоги) → AGENT 02 (требования) → AGENT 03 (реализуемость) → CISO / CLO (по триггерам) → решение Project Director (с владельцем, если меняется концепция) |
| Дизайн экрана | AGENT 10 (референсы) → AGENT 04 → CLO/CISO, если затронуты юридически значимые уведомления или безопасность пользователя |
| Новая зависимость | AGENT 03 + CISO + CLO |
| Каждый крупный этап | отчёт AGENT 10 с новыми идеями |
| Перед коммерческим запуском | AGENT 10 (позиционирование, монетизация) + CLO |

## 6. Разногласия и эскалация
1. Экспертное обсуждение; аргументы сторон фиксируются в документе задачи.
2. Варианты решения и фактические риски.
3. Устранение техническими/организационными мерами.
4. Если остаётся Critical/High, существенный юридический риск, риск утраты данных, платные услуги, изменение концепции, удаление ключевых функций, необратимые операции, публикация релиза или слияние в `main` — эскалация владельцу.
Project Director не может отменить отрицательное заключение CISO или CLO.

## 6a. Уровни решений (V4 §13)
- **LEVEL 1 — Project Director самостоятельно:** технические, организационные, кадровые, внутренние продуктовые решения.
- **LEVEL 2 — после консультации** (с профильными специалистами, CISO/CLO по триггерам): архитектурные изменения, новые функции в рамках MVP, средние остаточные риски, изменения организации.
- **LEVEL 3 — только владелец:** изменение концепции, окончательные платные функции, цены, платные сервисы, неустранимые Critical/High, существенные юридические риски, необратимые операции, публичный релиз, слияние в `main`.
Вопросы LEVEL 3 объединяются в одно обращение с рекомендациями и последствиями.

## 6b. Платные функции
Ни одна платная функция не считается утверждённой и не реализуется до решения владельца по `COMMERCIAL_PRODUCT_PROPOSAL.md`. Бесплатная версия не ограничивается искусственно; безопасность и приватность не снижаются ради монетизации.

## 7a. RACI и независимая приёмка (V7 §7)
В `BACKLOG.md`: **Исполнитель = Responsible**, **Руководитель = Accountable** (ровно один), **Проверяющий = Consulted** (независимая проверка), **Informed** — по умолчанию Project Director (и владелец для LEVEL 3). Разработчик не принимает собственную работу: Code Review — Lead команды или назначенный Senior; QA; Security/Legal Review — по триггерам §1.

## 7b. ADR
Существенные архитектурные решения — `docs/adr/` (контекст, проблема, альтернативы, решение, обоснование, последствия, проверка). Пересмотр принятого ADR — только при новых фактах, новым ADR со ссылкой «Supersedes».

## 8. Отчётность
После каждого существенного этапа — **краткий** отчёт владельцу (V7 §20: статус-метка, что сделано, что проверено, существенные риски, рекомендация директора, нужно ли участие владельца; метки [ГОТОВО] [В РАБОТЕ] [НА КОНТРОЛЕ] [РИСК] [БЛОКЕР] [РЕШЕНИЕ ВЛАДЕЛЬЦА] [РЕКОМЕНДАЦИЯ ДИРЕКТОРА] [СРОЧНО — SECURITY] [СРОЧНО — LEGAL]). Ранее (V3 ч. 14): завершено, проверено, кто работал, кто присоединился/повышен, исправленные задачи, блокировки, результаты QA/Security/Legal, самостоятельные решения, вопросы к владельцу. Промежуточная техническая переписка владельцу не направляется.
