# UPDATE_RELEASE_CHECKLIST — выпуск обновлений STABLE и EMERGENCY SECURITY

Статус: **проект (AGENT 03)** · Редакция 1 · 2026-11-10 · утверждают CISO, QA (AGENT 08), Release (AGENT 09), PD; GATE 10.
Основание: V7 §3 (процесс DISCOVER → TRIAGE → FIX → INDEPENDENT REVIEW → TEST → SIGN → PUBLISH → AUTO UPDATE → VERIFY), D-25, правило CLAUDE.md №6, процедура CISO Q-3 (`SECURITY_REVIEW.md` §4.2). Архитектура — `UPDATE_SECURITY_ARCHITECTURE.md` (далее [USA]); сбои — `UPDATE_FAILURE_RECOVERY.md`.
Детали процедуры EMERGENCY (кто и как одобряет вне рабочего времени) — будущий `EMERGENCY_PATCH_POLICY.md` (CISO); этот чек-лист — её обязательный минимум.

## 0. Кто подписывает

| Роль | STABLE | EMERGENCY SECURITY |
|---|---|---|
| Разработчик (Responsible) | FIX, PR | FIX, PR |
| Независимый ревьюер (не автор) | Code Review — Lead или Senior | то же, обязательно |
| CISO (или назначенный 07/14/15) | Security Review по триггерам | **обязательно**: подтверждает severity, достижимость, полноту фикса |
| QA (AGENT 08) | полный регресс | сокращённый обязательный набор §2 |
| Release (AGENT 09) | сборка, подпись, публикация | то же |
| CLO | при изменении лицензий/данных/текстов EULA | при изменении данных или юрисдикционных уведомлений |
| Project Director | GO на публикацию | GO на публикацию |
| **Владелец (LEVEL 3)** | **публичный релиз и слияние в `main` — явное подтверждение** | **в рамках заранее одобренной владельцем политики** (V7 п.11) — без отдельного подтверждения на каждый выпуск, если выполнены все условия §2 и `EMERGENCY_PATCH_POLICY.md`; владелец уведомляется немедленно ([СРОЧНО — SECURITY]); иначе — явное подтверждение |

Разработчик не принимает собственную работу; один человек/агент не может быть одновременно автором фикса и одобряющим ревьюером, CISO-одобряющим или держателем ключа публикации для того же выпуска.

## 1. Никогда не пропускается (в том числе в EMERGENCY)

1. Независимое ревью кода (не автор).
2. `scripts/check.sh` полностью зелёный; весь CI, включая Windows-job и macOS-job; `cargo deny`, `npm audit` без новых `ignore` (кроме оформленных по Q-3).
3. Тест, воспроизводящий уязвимость, падает до фикса и проходит после (или обоснование CISO, почему это невозможно).
4. Тесты обновления: обновление с **каждой** поддерживаемой версии ≥ `min_safe_version` на новую; отказ при подмене артефакта; downgrade отклонён.
5. Smoke-тест конвертации после обновления (синтетические строки, без реальных данных) на Windows 11, Windows 10 и macOS.
6. Сборка из тега в CI (не локально), воспроизводимые хэши wasm-модулей; SBOM обновлён.
7. Подпись: minisign-артефакт с `--app-version`, подпись манифеста ключом `release`; (после D-11) Authenticode / Developer ID + нотаризация; проверка подписей **после** загрузки с хоста.
8. Метаданные: `seq` больше предыдущего, `expires_at` задан, `min_safe_version` и `revoked_versions` проверены вторым человеком.
9. Проверка «нет пользовательских данных»: в запросах `ks-updater` нет версии/ID (тест [USA] §18 п.3).
10. Запись в журнал выпуска: что исправлено, advisory, кто одобрил, хэши.

## 2. Этапы

### 2.1 DISCOVER
- [ ] Источник: собственная находка, RUSTSEC/GHSA/CVE зависимости, отчёт исследователя (`SECURITY.md`), сбой у пользователя.
- [ ] Регистрация в закрытом трекере (GitHub Security Advisory draft — приватный); **никаких деталей в публичных issue/коммитах до выпуска**.
- [ ] Время обнаружения зафиксировано (старт SLA Q-3 §8).

### 2.2 TRIAGE (CISO, ≤ 24 ч для внешних отчётов)
- [ ] Severity (CVSS-подобная оценка + достижимость в нашей конфигурации).
- [ ] Канал: High/Critical достижимые → EMERGENCY; иначе STABLE.
- [ ] Нужна ли временная emergency-политика ([USA] §12) до фикса; если да — подготовить и подписать **отдельно** (шаги 2.6–2.8 для политики).
- [ ] Затронутые версии → кандидат в `min_safe_version` и `revoked_versions`.

### 2.3 FIX
- [ ] Ветка `fix/*` (EMERGENCY — от тега последнего STABLE, минимальный diff).
- [ ] Тест-воспроизведение.
- [ ] Новая/обновлённая зависимость — правило 3 или процедура Q-3 (возраст ≥ 72 ч, для Critical — ≥ 24 ч письменно CISO).

### 2.4 INDEPENDENT REVIEW
- [ ] Code Review (не автор).
- [ ] Security Review CISO: фикс закрывает причину, нет регрессий политики (`UserText`, сеть, права).
- [ ] Legal Review — по триггерам.

### 2.5 TEST
- [ ] Обязательный набор §1 п.2–5.
- [ ] STABLE: полный регресс QA, ручная приёмка по D-10 при изменении поведения полей; матрица Windows 10/11 и macOS.
- [ ] Тест обновления на тестовом канале с **тестовыми** ключами (никогда не продуктовыми).

### 2.6 SIGN (AGENT 09; ключи — только в секретах CI)
- [ ] Сборка из подписанного тега workflow `release` (Actions закреплены по SHA).
- [ ] Environment `release` одобрен: STABLE — владелец; EMERGENCY — по `EMERGENCY_PATCH_POLICY.md`.
- [ ] `tauri signer sign --app-version <v>` (Tauri CLI ≥ 2.12.4) для каждого артефакта; подпись кода ОС (после D-11).
- [ ] Генерация `channel/*.json`, подпись `release`; `timestamp.json` — подпись `timestamp`.
- [ ] Проверка подписей независимым шагом CI тем же кодом `ks-update-core`, что у клиента.

### 2.7 PUBLISH
- [ ] Слияние в `main` — **только с подтверждения владельца** (правило 6) либо по заранее одобренной EMERGENCY-политике.
- [ ] Артефакты → GitHub Release версии; метаданные → релиз `updates-meta` (порядок: артефакты → манифест → `timestamp` последним).
- [ ] Повторная загрузка с публичного URL и проверка хэшей/подписей.
- [ ] Публикация advisory (после того как обновление доступно; EMERGENCY — одновременно или после достижения 100 %).

### 2.8 AUTO UPDATE (поэтапный выпуск)
| Этап | STABLE | EMERGENCY |
|---|---|---|
| Канарейка | внутренние машины (владелец, QA) ≥ 24 ч, `percent = 0` + ручная установка | внутренние машины ≥ 1 ч (Critical: ≥ 30 мин) |
| 1 | `percent = 5`, ≥ 24 ч | `percent = 100` |
| 2 | `percent = 25`, ≥ 48 ч | — |
| 3 | `percent = 100` | — |
- [ ] Каждое изменение `percent` — новый `seq` манифеста + `timestamp`.
- [ ] Критерии остановки (`halted = true`): любой подтверждённый отчёт о сбое запуска, потере данных, неверной замене текста; провал health-check на канарейке. Телеметрии нет — источники: канарейки, CI, обращения.

### 2.9 VERIFY
- [ ] Через 24 ч и 7 дней: нет открытых отчётов о регрессиях; при STABLE — решение о следующем этапе.
- [ ] Журнал выпуска закрыт; `RISK_REGISTER`/`SECURITY_REVIEW` обновлены (статус SEC-xx).
- [ ] Ретроспектива для EMERGENCY (что ускорить, что нельзя было пропустить).
- [ ] Проверка, что ежедневное переподписание `timestamp` работает (иначе клиенты увидят «не проверялись» через 7 дней).

## 3. Отдельные чек-листы
- **Emergency-политика без новой версии:** TRIAGE → черновик JSON (только ключи из [USA] §12) → ревью CISO + PD → подпись `policy` → публикация → проверка загрузки на канарейке → срок ≤ 30 дн. → снятие при выходе фикса.
- **Ротация ключа `release`/`timestamp`/`policy`:** только через новый `root.json` (офлайн-церемония 2 из 3, LEVEL 3); тест на тестовом канале; публикация; старые подписи остаются валидными до истечения сроков файлов.
