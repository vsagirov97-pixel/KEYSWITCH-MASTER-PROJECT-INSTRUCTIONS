Статус: **требования CISO.** Выбор конкретных механизмов, поставщиков и покупок — **LEVEL 3, решение владельца** (V7 п. 11: «изменение корневой системы доверия и механизмов подписи»; D-11, D-22(6)). Отмечено меткой **[LEVEL 3]**.

## 1. Принципы (обязательны для всех ключей)

1. **Разделение ролей ключей:** корень доверия обновлений ≠ ключ подписи выпусков ≠ ключ emergency-политик ≠ сертификаты подписи кода ОС. Компрометация одного не должна давать полномочий другого.
2. **Наименьшие полномочия и наименьшая доступность:** чем выше роль, тем реже используется и тем дальше от сети (корень — офлайн).
3. **Правило двух лиц** для операций с корнем и для каждого выпуска (подтверждение environment) — там, где это возможно; где невозможно — компенсирующие меры (§5.3).
4. **Ключи никогда не находятся:** в репозитории (включая историю, ветки, issues, PR, Actions logs), в исходном коде, во фронтенде и `dist/`, в бинарях (кроме **публичных** ключей), в журналах приложения и CI, в артефактах сборки, в переменных окружения облачных сессий разработки, **в контексте, файлах или инструментах ИИ-агентов** (ни один агент, включая Project Director и CISO, не получает доступа к секретам, паролям ключей, токенам HSM/KMS; агенты не считаются «вторым лицом»), в мессенджерах и почте.
5. **Подпись — только воспроизводимым процессом** (релизный workflow), с журналом каждой подписи (§8). Ручная подпись на ноутбуке — запрещена, кроме церемоний корня (§4).
6. **Проверка независима от подписи:** после подписи артефакт проверяется отдельным шагом встроенным публичным ключом предыдущей версии (`EMERGENCY_PATCH_POLICY.md` §9 п. 8).
7. **Отказ при сомнении:** клиент не принимает обновление при любой ошибке проверки; в релизных сборках нет флага «принять без подписи» и нет переопределения ключа из настроек/реестра/переменных окружения.

## 3. Механизм подписи обновлений — требования к выбору [LEVEL 3]

Решение принимает владелец по проекту AGENT 03 и заключению CISO. Требования CISO к любому варианту:
- Подпись **метаданных и пакета** (хэш пакета в подписанных метаданных); подпись — асимметричная (Ed25519 или эквивалент), проверка в клиенте до установки.
- **Отдельный корень и отдельный ключ выпуска** (не единственный ключ, встроенный в бинарь, которым подписывается каждый релиз). Если выбранный инструмент поддерживает только один встроенный публичный ключ (по документации Tauri 2 `tauri-plugin-updater` принимает один `pubkey` — **UNVERIFIED**, в этой сессии не перепроверено) — разделение ролей и ротация обеспечиваются собственным слоем: встроенный корень проверяет подписанный список ключей выпуска; иначе CISO вариант **не одобрит** без письменного принятия владельцем остаточного риска (ротация только через «последний выпуск старым ключом», восстановление при утрате ключа — только переустановкой вручную).
- Защита от отката (монотонная версия, минимально допустимая версия в подписанных данных), от заморозки (срок годности метаданных), от подмены платформы/архитектуры, от смешивания метаданных разных выпусков.
- Возможность порога (например, 2 из 3 корней) — желательна; минимально — **два независимых корня**, любой из которых может переподписать список ключей (резерв на случай утраты), с правилом двух лиц на церемонии.
- Ориентир — модель ролей The Update Framework (root/targets/snapshot/timestamp); полная реализация TUF не требуется, но каждая отсутствующая роль должна быть обоснована в `UPDATE_SECURITY_ARCHITECTURE.md`.

## 4. Церемонии корня (K-1)

**Генерация** (однократно, до GATE 10):
1. На изолированном устройстве без сети (или непосредственно на аппаратном токене с неэкспортируемым ключом); присутствуют владелец и второе лицо (§5.3); ИИ-агенты не участвуют и не получают материалы.
2. Генерируются K-1a и K-1b на **разных** носителях; для каждого — резервная копия (§7).
3. Записываются отпечатки публичных ключей; протокол церемонии (дата, участники, носители, отпечатки — **без** секретов) — подписывается участниками и хранится у владельца; копия протокола без секретов — в `docs/security/`.
4. Подписывается первичный список доверенных ключей (K-2, K-3, при наличии K-4) со сроком действия ≤ 12 мес.
5. Публичные K-1a/K-1b встраиваются в исходный код через PR с ревью CISO (сверка отпечатков двумя лицами).

**Плановое продление списка ключей** (≤ 12 мес.): та же процедура без генерации корня; новый список публикуется через обычный выпуск.

## 5. CI-секреты и правило двух лиц

### 5.1 GitHub Actions
- Отдельный **релизный workflow** (не `ci.yml`), триггер — только тег `v*` из защищённой ветки; ветки и PR из форков доступа к секретам не имеют; `pull_request_target` запрещён.
- **Environments** `release`, `release-emergency`, `policy-emergency`: обязательные ревьюеры (владелец; второй — если появится второй доверенный человек), ограничение по тегам/веткам (`deployment branch policy` — только защищённые), запрет самоодобрения автором запуска, где поддерживается.
- Секреты K-2/K-3/K-6/K-7/K-9 — **только на уровне environment**, не репозитория и не организации.
- `permissions:` по умолчанию `contents: read`; `id-token: write` и `attestations: write` — только в job подписи/аттестации; подписывающий job не запускает сторонний код, кроме закреплённых по SHA actions из утверждённого списка, и не выполняет `npm install`/скрипты сборки (сборка — в предыдущем job, подпись — над артефактом с проверкой хэша).
- Секреты не выводятся: маскирование включено, `set -x` запрещён в шагах с секретами, ключ из файла удаляется в `always()`-шаге; на macOS — временная связка ключей удаляется в конце job.
- Обязательные предпосылки (зависят от владельца): защита `main`, secret scanning + push protection (SEC-39). **Без них GATE 10 не пройдёт.**

### 5.2 OIDC
Если ключи в облачном KMS/HSM или у поставщика облачной подписи — доступ только через OIDC-федерацию GitHub → облако с условием на `repo`, `environment` и `ref` (тег); долгоживущие API-ключи не используются. Права учётной записи — только `sign` для конкретного ключа, без `export`/`delete`/управления политиками. **[LEVEL 3]** — выбор и оплата KMS/HSM/службы подписи.

### 5.3 Правило двух лиц
- Каждый выпуск: инициатор (запуск workflow по тегу; тег ставит релиз-инженер/PD через PR) + **подтверждение обязательного ревьюера environment** (владелец). Для EMERGENCY — то же (`EMERGENCY_PATCH_POLICY.md` §4, §13 п. 2).
- Церемонии корня: владелец + второе доверенное лицо. **Сейчас в проекте один человек (владелец); ИИ-агенты вторым лицом не являются.** Компенсирующие меры, пока второго лица нет: токен с PIN и ограничением попыток; резервная копия разделена на доли (например, схема разделения секрета 2 из 3) с хранением в разных местах; видео- или письменный протокол церемонии; отпечатки сверяются по двум независимым каналам. Назначение второго лица — **[LEVEL 3]**.

## 6. Сертификаты ОС

### 6.1 Windows (K-5)
- Подписываются все исполняемые файлы и установщики, включая `ks-sandbox.exe` и апдейтер; метка времени RFC 3161 обязательна (подпись остаётся действительной после истечения сертификата).
- Апдейтер проверяет **и** подпись обновления (K-2), **и** Authenticode пакета (издатель = ожидаемый субъект/отпечаток из подписанных метаданных). Authenticode — дополнительный, не единственный контроль.
- Варианты (OV, EV, облачная служба подписи Microsoft или CA) — **[LEVEL 3]**, оплата — отдельное согласование (D-22(6)). Позиция CISO: облачный HSM/служба с OIDC предпочтительнее физического токена в руках одного человека (меньше риск утраты, есть журнал); EV не считать гарантией репутации SmartScreen (по публичным данным Microsoft изменила это поведение — **UNVERIFIED**).

### 6.2 macOS (K-6, K-7)
- Developer ID Application + hardened runtime + нотаризация + staple для бандла и **каждого** вложенного исполняемого файла; entitlements — минимальные и **раздельные**: основной процесс без `allow-jit`; JIT-entitlement — только для помощника песочницы и только если выбран Cranelift (SEC-55).
- Разрешения TCC (Accessibility) привязаны к подписи приложения (designated requirement, Team ID): **смена Team ID или bundle id сбрасывает выданные пользователем разрешения** и меняет доверие апдейтера — это изменение корня доверия на macOS **[LEVEL 3]**. Плановая замена сертификата в рамках того же Team ID допустима без сброса (проверить на CI-раннере при первой ротации — **UNVERIFIED**).
- Апдейтер проверяет подпись K-2 и `codesign --verify --deep --strict` / соответствие Team ID нового бандла до замены.

## 7. Резервное копирование

| Ключ | Резерв | Правило |
|---|---|---|
| K-1a, K-1b | по одной зашифрованной резервной копии (или доли разделённого секрета) каждого, в **разных** физических местах, отдельно от основного носителя | проверка восстановления — при генерации и ежегодно (без подключения к сети) |
| K-2, K-3, K-4 | **не резервируются** — при утрате выпускаются новые и переподписываются корнем | утрата ≠ инцидент, если нет признаков компрометации |
| K-5 | у поставщика (облачный HSM) или перевыпуск сертификата | — |
| K-6, K-7 | `.p12` в зашифрованном виде у владельца (офлайн) + перевыпуск через Apple | — |

## 8. Журнал подписей и прозрачность

- Каждая подпись (K-2, K-3, K-5, K-6) фиксируется: версия, платформа, архитектура, SHA-256 артефакта, ID запуска workflow, кто подтвердил environment, время. Источник — журнал Actions + provenance-аттестация (`attest-build-provenance`), публикуемые `SHA256SUMS`.
- Еженедельная сверка (AGENT 09, контроль CISO): каждая подпись в журнале соответствует выпуску; подпись без выпуска — **инцидент** (§10).
- Публичный список выпусков с хэшами позволяет третьим лицам обнаружить подписанный, но не объявленный пакет.

## 9. Ротация, отзыв и переустановка доверия

### 9.1 Плановая ротация
- **K-2/K-3:** новый ключ подписывается корнем в новом списке доверенных ключей; клиент принимает список, если он подписан действующим корнем (порог — по §3) и номер версии списка выше текущего; старый ключ удаляется из следующего списка; перекрытие — не дольше одного цикла выпуска.
- **K-1 (корень):** новый корень вводится выпуском, в котором новый список корней подписан **и старым, и новым** корнем (порог по старому набору); клиенты, пропустившие промежуточные выпуски, проходят цепочку списков корней последовательно (клиент хранит историю версий списка).
- **K-5/K-6:** продление до истечения; метки времени сохраняют действительность старых подписей.

### 9.2 Отзыв
- Компрометированный K-2/K-3 исключается новым списком, подписанным корнем, и публикуется как EMERGENCY (Critical). Клиенты, получившие список, отвергают всё, подписанное отозванным ключом, включая уже скачанные пакеты.
- Отзыв K-5: через CA с датой отзыва, предшествующей первой несанкционированной подписи (по журналу §8). Отзыв K-6: через Apple; запрос в Apple на отзыв нотаризации вредоносных сборок (порядок — **UNVERIFIED**, уточнить по документации Apple при инциденте).

### 9.3 Переустановка доверия (путь обновления встроенного публичного ключа)
1. **Штатный путь:** обновление, подписанное действующим доверенным ключом, несёт новый корень/список (9.1). Требует, чтобы хотя бы один корень не был скомпрометирован.
2. **Резервный корень:** если скомпрометирован или утрачен K-1a — K-1b подписывает новый список корней (без K-1a); поэтому **два независимых корня обязательны** (§3).
3. **Внеполосный путь** (оба корня скомпрометированы/утрачены): автоматическое обновление **прекращается** (клиент отвергает всё); бюллетень с указанием вручную скачать установщик, проверяемый Authenticode/нотаризацией (K-5/K-6) и опубликованными хэшами/provenance; новая версия содержит новые корни. Это **недопустимо как плановый путь** и означает, что пользователи, не прочитавшие бюллетень, остаются без обновлений — фиксируется в реестре как остаточный риск SEC-40.

## 10. Реагирование на компрометацию ключа (уровень инцидента — **Critical**)

Признаки: подпись без выпуска в журнале §8; утечка секрета (secret scanning, сообщение); подозрительный запуск релизного workflow; утрата токена/носителя; компрометация учётной записи владельца или GitHub-организации; сообщение о подписанном нашим ключом вредоносном файле.

## 11. Сводка решений LEVEL 3 (владелец)

1. **Корень доверия обновлений:** алгоритм, число корней (рекомендация CISO — 2, порог 1 из 2 для восстановления, 2 из 2 для плановой смены корня, когда появится второе лицо), носители (аппаратные токены — покупка).
2. **Механизм подписи обновлений:** готовый (`tauri-plugin-updater`/minisign) с собственным слоем списка ключей, TUF-подобный или собственный — по проекту AGENT 03 и заключению CISO.
3. **Платное хранение ключей:** облачный KMS/HSM или служба подписи (с OIDC) vs аппаратный токен.
4. **Сертификат подписи кода Windows:** тип и поставщик (D-11; без него SEC-19 открыт, публичный релиз CISO не пропускает).
5. **Apple Developer Program** (Developer ID, нотаризация), на чьё имя/организацию (связано с D-23) — **смена Team ID в будущем = смена корня доверия на macOS**.
6. **Второе доверенное лицо** для церемоний и подтверждения выпусков (или принятие компенсирующих мер §5.3).
7. **Хост раздачи обновлений** (GitHub Releases или собственный домен) — влияет на K-8, приватность (CLO) и стоимость.
8. **Заранее одобренный автоматизированный процесс** EMERGENCY-выпуска (V7 п. 11) — кто подтверждает environment.
